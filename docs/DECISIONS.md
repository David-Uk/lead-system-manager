# Decisions & Assumptions

- **WhatsApp Override:** The workplan mentions Telegram for staff alerts. We are ignoring that. ALL messaging, customer-facing and staff-facing, goes through WhatsApp via the WhatsApp adapter. No Telegram, Slack, or email. "Telegram" in the workplan means "WhatsApp staff notification".
- **WhatsApp Adapter:** Production uses Cloud API. We default to "simulated" mode where messages are logged to standard output/file but not actually sent.
- **LLM Provider - Ollama Cloud:** The hybrid classifier's LLM step uses the Ollama Cloud API (`https://ollama.com`, default model `gpt-oss:120b`) with an API key. There is no local Ollama setup and none should be assumed: `OLLAMA_BASE_URL` defaults to the cloud endpoint and `LLM_PROVIDER=ollama` refuses to boot without `OLLAMA_API_KEY`. The adapter exposes one `classifyWithLlm(text)` interface over three providers (gemini/groq/ollama) so swapping providers is an env change only.
- **Classifier Degradation:** Rules run first and always; the LLM is consulted only below `RULES_CONFIDENCE_THRESHOLD` (0.7). If the provider fails, times out or answers below `CONFIDENCE_THRESHOLD` (0.6), the system answers from the rules opinion when available - or asks a clarifying question / hands off to a human - and records a `CLASSIFIER_FALLBACK` audit event. Customer service never depends on the AI being up.
- **Order Stock Handling:** The slot-filling flow checks stock when an item is chosen and re-checks it at confirmation, but creating an order never decrements product stock. Inventory is treated as "checked at order time, fulfilled by staff": the team confirms physical stock and moves the order through `confirmed` -> `dispatched` -> `delivered` via the staff API. Revisit when payment or real stock synchronisation lands.
- **Lazy Expiry of Collecting Conversations:** A slot-filling conversation idle for 30+ minutes is expired lazily - on the next inbound message it is marked `EXPIRED` and a fresh conversation is opened, then that message is processed normally (it does not get an "expired" reply, nor is it force-fed into the stale question). This avoids cron jobs while guaranteeing a customer answering an old question never silently mutates an abandoned order draft.
- **Ticket References & SLA:** Tickets use a single global `TKT-0001` sequence (count-based, with a unique-index retry when two escalations race the counter), not the daily `ORD-YYYYMMDD-####` style used for orders. Tickets are low volume and staff quote their reference verbatim on the phone, so a short stable id beats a dated one. `overdue` is never stored: it is derived at read time as "status `open` and older than `TICKET_SLA_MINUTES` (default 15)", so the flag can never go stale between writes.
- **Staff Notifications:** New tickets are announced to `STAFF_WHATSAPP_NUMBER` through the same WhatsApp adapter - staff alerts and customer replies share one channel (see WhatsApp Override above). Delivery is best-effort: up to 3 attempts with backoff, and the notifier never throws, because the ticket already exists and is the source of truth. The outcome lands on the ticket (`notificationStatus` `pending` -> `sent`/`failed`) and in the audit trail (`NOTIFICATION_SENT`/`NOTIFICATION_FAILED` with the destination masked by `maskPhone`). That pair is what failure #4 ("the dashboard flags tickets nobody was alerted about") reads; a dead channel is visible, never silent.
- **Audit API Pagination:** `GET /api/audit` uses keyset cursor pagination (opaque base64url `createdAt|_id` cursor) instead of offset pages, because the trail is written continuously - offset pages would skip or repeat events between requests. Ordering is newest-first with `_id` breaking `createdAt` ties, so the cursor stays stable even for events saved in the same millisecond.
- **Dashboard:** The operations dashboard is a static, dependency-free page (no build step) served under `/dashboard`, rendered exclusively with `textContent` DOM updates and a route-specific CSP. The staff key is prompted for and kept in `sessionStorage` (never a cookie, never the URL); without a key the page still renders its shell and shows an auth notice instead of failing. All numbers come from the two staff APIs (`/api/metrics`, `/api/audit`) - the dashboard has no backend of its own.
- **API Documentation:** The OpenAPI 3.0 document is hand-authored (`src/openapi/document.js`) rather than generated from the zod schemas: the schemas describe request validation, while the document must describe responses, status codes and examples; a drift-guard test pins the documented paths to the mounted routes. RapiDoc is self-hosted from `node_modules` (resolved via `createRequire`), so `/docs` works offline with no CDN dependency. Only implemented endpoints are documented - workplan sections 8.4/8.5 (products staff API) and 8.12/8.13 (conversations staff API) have no owning sprint task and are deliberately absent until they are built.
- **Metrics Definitions:** `GET /api/metrics` deliberately mixes two time scopes: period-scoped figures (messages, conversations, intents, orders, failures, response times) come from the `from`/`to` window (default last 24 h), while `tickets` and `unresolvedConversations` are live snapshots of the current backlog. The payload names the period explicitly so the dashboard can label each number honestly. `escalationRate` = tickets created in the window / conversations with activity in the window (0 when there are none), and `avgAutoResponseMs` pairs `MESSAGE_RECEIVED` -> `REPLY_SENT` per correlation id.
